# 地域サービス_クラス図作成ガイドライン

## 1. 目的
本ガイドラインは、スマートシティのデータモデルを定める、実装データモデル・地域サービス・データモデル・ガイドブックに記載されるデータモデルの相互運用性を確保するため、データモデルのクラス図作成のための設計原則を定めるものである。

## 2. クラス図作成ガイドライン

### 2.1 識別子の扱い
- **Primary ID**: 各クラスの先頭属性として定義する。命名は `[objectName]Id` とする（例：`shelterId`）。
- **Foreign ID**: クラス図上には属性（プロパティ）として記述せず、クラス間の**関係線**を引く。線の端に多重度（`"1"`, `"0..*"` 等）を記述する。

### 2.2 単位の扱い
- **単位の扱い**: 物理量（Measure）を扱うプロパティは、定義書または制約事項に単位（例：mm, m, kg）を明示する。

### 2.3 共通クラスの適用
- 全ての地域サービスが共通で持つ属性は `AbstractSmartCityBase` クラスとして定義し、各ドメインはこれを継承（Generalization）する。
- 共通属性の定義には、**GIF（政府相互運用性フレームワーク）**のコアデータモデルや標準メタデータを積極的に採用し、国や他システムとの相互運用性を確保する。
- 共通属性の例：`識別子 / identifier`, `名称 / name`, `作成日時 / createdDateTime`, `更新日時 / modifiedDateTime` 等

### 2.4 プレフィックスの除外
- ガイドライン内の記述にかかわらず、今回の出力ではプレフィックス（`pd:`等）を一切付与せず、純粋な名称のみを使用する。

### 2.5 ISO/IEC 11179 のその他関連パートの補足
- **Part 4 (定義の策定ルール)**: 「項目名」だけでなく、第三者が誤解しない「定義文」をセットで記述すること。
- **Part 6 (登録)**: 確定した項目に「管理番号」を振り、バージョニングを行うこと。

## 3. クラス図記述ルール (EAツール前提 / UML 2.x 準拠)

本プロジェクトでは、Enterprise Architect (EA) 等のツールを用いたモデリングを前提とし、以下の記法を標準とする。

### 3.1 クラスと属性の表記

クラスおよび属性には、以下の要素を定義する。「日本語論理名」と「英語論理名」を入力することで、論理名（英語）と論理名（日本語）の対応をツール上で管理する。なお、論理名（英語）は物理名として利用できる前提とする。

#### A. クラス (Class)
- **クラス名 (Name)**: 日本語の論理クラス名（例: `住所`）にアンダースコアを繋ぎ、英語の論理クラス名（別名）を記述する。（例: `住所_Address`）
- **ステレオタイプ**: クラスの性質を表す場合に付与。（例: `<<DataType>>`, `<<Enumeration>>`）

#### B. 属性 (Attribute)

記述フォーマット: `+ 日本語論理名 / 英語論理名 : データ型 [多重度]`
EAツールへのインポートおよび視認性を両立するため、スラッシュ（/）区切りで両方を記述し、その後に正式なデータ型を添えること。

| 要素 | 可視性 | 名前と別名 | 型 | 多重度 |
| :--- | :--- | :--- | :--- | :--- |
| **表記ルール** | 原則 `+` (Public) | `日本語論理名 / lowerCamelCaseの英語論理名` | 定義済みの論理データ型（※半角カッコ不可） | `[1]`, `[0..1]`, `[0..*]` を明記 |
| **記述例** | `+` | `都道府県 / prefecture` | `文字列` | `[0..1]` |

EAでの入力・Mermaid出力イメージ:
- `+ 収容可能人数 / capacityCount : 数値（整数） [0..1]`
※注意：Mermaidパーサーが関数（メソッド）と誤認するのを防ぐため、型表記に半角カッコ `()` は絶対に使用せず、**全角カッコ `（）`** を使用すること。

### 3.2 関係線の使い分け基準
関係性は「参照」か「所有」かの2種類で厳密に使い分けること。迷った場合は「関連」を選択する。

| 種類 | 記号 (Mermaid) | 適用ルール (ライフサイクル基準) |
| :--- | :---: | :--- |
| **関連 (Association)** | `-->` | **「参照」**。互いに独立しており、IDを知っているだけの関係。<br>親が削除されても子は残る。<br>（例：避難所が自治体マスターを参照する） |
| **コンポジション (Composition)** | `*-->` | **「所有」**。親が削除されたら子も同時に削除される**強い親子関係（運命共同体）**。<br>子は親の一部であり、単独では存在し得ない。<br>（例：避難所が共通型である住所を所有する） |
| **汎化 (Generalization)** | `<|--` | **「継承」**。共通クラス（`AbstractSmartCityBase`等）を継承する場合に使用。 |

### 3.3 多重度 (Multiplicity) の定義
属性およびリレーション端には、必ず多重度を明記する。

| 表記 | 意味 | 備考 |
| :--- | :---: | :--- |
| **`"1"`** | 必須 (Exactly One) | NULL不可。必ず1つ存在する。 |
| **`"0..1"`** | 任意 (Zero or One) | NULL可。存在しない場合がある。 |
| **`"0..*"`** または **`"*"`** | 複数 (Zero or More) | リスト。0件の場合もある。 |
| **`"1..*"`** | 1以上 (One or More) | 少なくとも1件は必須。 |

## 4. クラス図の作成手順

### 4.1 事前準備（入力ファイルの読み込み）
クラス図の作成にあたり、本資料以外に以下のファイルを生成AIに読み込ませ、「これら2つのCSVの内容をUMLとして図解すること」を指示する。
1. **地域サービス_データモデル.csv**: 論理名・英語名・型・多重度を含む正解データ。
2. **地域サービス_コード定義.csv**: 各項目の選択肢（値リスト）の定義データ。

### 4.2 クラス図作成の基本方針
- **ドメイン単位の出力**: 巨大な図の一括生成は避け、必ず「分類（ドメイン）」単位、またはさらに細分化した「サブカテゴリ」単位で出力すること。

- **対象ドメインの特定と分割戦略**:
  生成AIは、CSVの `分類` カラムおよび `地域サービス・データモデル・ガイドブック.md` 第4章の構成に基づき、以下の単位で図を作成する。
  - **通常ドメイン**: 1分類1図として作成（土地、建物、設備、道路、交通関連施設、移動オブジェクト、イベント・アクション、行政情報、センサーデータ等）。
  - **巨大ドメイン（施設）**: 「4.3 施設」については、以下の2段階に分けて図を作成する。
    - **(1) 施設共通図**: 「施設基本モデル」と、それに紐づく共通型（住所型、連絡先型、アクセシビリティ型等）の関係を示す。
    - **(2) 専門施設別図**: 医療機関(4.3.3)、教育機関(4.3.4)、介護(4.3.5)等のサブカテゴリごとに作成する。この際、「施設基本モデル」を継承（Generalization）し、カテゴリ固有 of 追加属性のみを記述すること。

### 4.3 属性およびリレーションの定義ルール

生成AIは、出力するクラス図において以下のUML記法および設計規則を厳守すること。

- **属性の表記形式**: `+ 日本語論理名 / 英語論理名 : データ型 [多重度]` 形式で記述する。型情報の脱落は厳禁とする。
- **共通クラスの継承**: 全ドメインのクラスは、共通属性を持つ `AbstractSmartCityBase` クラスを継承（`AbstractSmartCityBase <|-- 対象クラス`）していることを明示する。
- **識別子（ID）の処理**:
    - Primary ID : 各クラスの先頭属性として配置する。命名は `[objectName]Id` とする。
    - 外部参照ID/コード（守備範囲外）: 「全国地方公共団体コード」「町字ID」「郵便番号」「座標参照系コード」など、システム外部の巨大なマスタに依存する項目は、独立したクラス（箱）は作らず、属性内にインラインで `: コード（文字列） [0..1]` や `: ID（文字列） [0..1]` と型記述するのみ（関連線も引かない）で処理すること。
- **Foreign ID（他クラス参照）の処理**:
     - 本モデル内で定義されている他クラス（例：施設が住所を呼ぶ等）を参照する場合は、属性リストからは除外し、3.2項の「ライフサイクル基準」に従って、多重度を付与したコンポジション（`*-->`）または関連（`-->`）の線で表現すること。
     - 「住所」「連絡先」「アクセシビリティ」「画像」などの共通型クラスを他ドメインから参照する場合は、原則として一律で**コンポジション（`*-->`）**の線で表現すること。
- **多言語属性の集約ルール**:
    - CSV内で「項目名」「項目名カナ」「項目名英字」（英語名が `~`、`~Kana`、`~En`）のように3行に分かれている多言語セットを検出した場合、これらを独立した属性として出力せず、末尾のサフィックスを剥ぎ取ったベース名に一元統合し、型に `多言語文字列型_MultilingualString` を指定すること。
- **リレーションの多重度表記**:
    - 関係線の多重度は、接続名（ラベル）の中に埋め込まず、必ずクラス名の直後にダブルクォーテーションで囲んで記述（例：`住所_Address "1" *--> "0..*" 多言語文字列型_MultilingualString`）し、UML標準規格に準拠させること。

### 4.4 クラス図（Mermaid形式）の出力と運用

1. **Mermaid記法による出力**
   生成AIに、Markdown上でプレビュー可能なMermaid記法のコードブロック（```mermaid ~ ```）を出力させる。
   - **自動ソート・メソッド化エラー対策（最重要）**: クラスの `{}` 内に人間用の見出し（★表記やセクション区切り文字）を直接記述すると、Mermaidの自動ソート仕様により表示が崩れ、さらに半角カッコ `()` が混入するとメソッド（関数）として誤認識される原因となる。そのため、人間用のカテゴリ分けや見出しは、図の属性欄には入れず、ソースコード上のコメントアウト（`%%`）としてのみ記述すること。また、型表記のカッコは必ず全角 `（）` とすること。
   - **物理量（単位）の記述ルール**: 属性に対応する単位（人、m2、台など）をソースコード内に残す場合は、属性と同じ行の後ろ（インライン）には記述せず、必ず**「対象属性の直後の行に、インデントを下げて独立したコメント行（`%% 単位:〇〇`）として記述」**すること。
   - **Namespaceによる構造化**: 図の肥大化を防ぎ視認性を高めるため、メインクラス以外の「共通クラス（Components）」や「コード・リスト定義クラス（Enumeration）」を出力する際は、それぞれ `namespace 共通クラス { ... }` や `namespace コード定義 { ... }` などの名前空間構文を用いてグループ化すること。
   - **コード定義の反映**: コードマスタに定義がある項目については、適宜 `class クラス名 <<Enumeration>>` として図中に描き、対象クラスから関連線を引くこと。
   - **肥大化防止ルール**: コードリストの選択肢（値）が5つ以上ある、または膨大な場合は、Mermaid内にすべての値を書き込まず、クラス内に「%% ※詳細はコードマスタ参照」とコメントを記述し、図の肥大化とレンダリングエラーを防止すること。選択肢が4つ以下の場合は、`符号 : 日本語ラベル` の形式で列挙してよい。

   * **出力イメージ（施設共通モデルの基本構造）**:
     ```mermaid
     classDiagram
       direction TB

        class AbstractSmartCityBase {
            + 識別子 / identifier : 文字列 [1]
            + 名称 / name : 文字列 [0..1]
            + 作成日時 / createdDateTime : 日時 [0..1]
            + 更新日時 / modifiedDateTime : 日時 [0..1]
        }
       
       class 施設_Facility {
         + ID / id : ID（文字列） [0..1]
         + 施設種別 / category : コード（文字列） [1]
         + 名称 / name : 多言語文字列型_MultilingualString [0..1]
         + 通称 / alternateName : 文字列 [0..1]
         + 説明 / description : 文字列 [0..1]
         + アクセス方法 / accessMethod : 文字列 [0..1]
         + 駐車場有無 / parkingStatus : コード（文字列） [0..1]
         + 収容人数 / capacity : 数値（物理量） [0..1]
           %% 単位:人
       }
       
       namespace 共通クラス {
           class 住所_Address
           class 連絡先_ContactPoint
           
           class 多言語文字列型_MultilingualString <<DataType>> {
               + 日本語 / ja : 文字列 [1]
               + カナ / kana : 文字列 [0..1]
               + 英字 / en : 文字列（半角） [0..1]
           }
       }
       
       namespace コード定義 {
           class 有無コード_StatusCode <<Enumeration>> {
               0 : 無
               1 : 有
               2 : 非公開
               9 : 不明
           }
       }

       %% リレーション（UML/Mermaid標準準拠）
       AbstractSmartCityBase <|-- 施設_Facility
       施設_Facility *-- "1" 住所_Address : 施設住所_buildingAddress
       施設_Facility *-- "0..*" 連絡先_ContactPoint : 連絡先情報
       施設_Facility "1" --> "0..1" 有無コード_StatusCode : 有無参照
       施設_Facility "1" *--> "0..*" 多言語文字列型_MultilingualString : 内包
     ```

2. **繰り返し実行と確認**
   - 担当者は、CSVから処理したい `分類` を順次指定し、各ドメインの図が確定するまで対話を継続すること。
