# 地域サービスデータモデル_作成ガイドライン

## 1. 目的
本ガイドラインは、「地域サービス・データモデル・ガイドブック」で定義されるデータモデルを抽出し、命名規則に基づく英語論理名の付与、データ型の定義、正規化、構造化を行い、ドメイン別クラス定義を行うことを目的とする。
なお、ここで構造化された論理データモデルは、別作業にて実施されるセマンティック・データモデル作成（JSON-LD化）へ引き継ぐものとする。

---

## 2. 実装プロセス
STEPごとに生成AIを対話的に活用しながら抽出作業を進めることを想定する。これにより、生成AI特有のハルシネーションやコンテキストロストの発生を抑止する。
なお、下記実行プロセスは「生成AIとのチャット形式での実施」を基本として記載しているが、担当者の技術的な習熟度に応じ、より効率的な手法を採用しても構わない。例えば、Python等を用いた生成AIのAPI連携（処理の自動化）や、Function Calling（AIに外部ツールの自動実行やファイル保存等の「スキル」を持たせる仕組み）による完全自動化、CLIツールでの生成AI実行など、実現手段は柔軟に変更できるものとする。

**【共通ルール：生成AIによるCSV出力と手動保存の運用】**
チャット形式で実施する場合、手動でのコピー＆ペーストによる行欠落やフォーマット崩れを防ぐため、以下の運用ルールとすることを推奨する。
- **全件結合出力:** 各チャンクの処理中はその都度CSVを出力させず、生成AIのメモリ上にデータを保持させる。対象の全分類の処理が完了した段階で、生成AIに「全件結合済みのCSV形式コードブロック」を一度だけ出力させ、担当者がそれをローカルファイルに手動で保存（または上書き保存）する。
- **出力が途切れた場合のリカバリー手順:** データ量が多く、生成AIの文字数制限によってCSVコードブロックの出力が途中で切れた（停止した）場合は、生成AIに対し**「途切れた行の続きから、最後までCSVコードブロックで出力してください」**とプロンプトを入力する。出力された続きのテキストをコピーし、ローカルのCSVファイルの末尾に手動で追記して結合すること。

**【注記：高度な実装の検討事項】**
地理空間情報のSchemaとの整合を確認する場合、国土交通省のMCPサーバー等の活用ができるのであれば、CLIからのAPI呼び出しによる確認の実施も担当判断とする（※PLATEAU対応が可能かについては別途要確認）。

### 事前準備：生成AIのセットアップ（司令塔プロンプト）
作業を開始するにあたり、担当者は生成AIの新しいチャットセッションを立ち上げ、本ガイドライン（`01_地域サービスデータモデル_作成ガイドライン.md`）をアップロード（または全文コピー）した上で、以下の**プロンプト（メタプロンプト）**を入力し、生成AIに全体の作業手順を認識させること。

**▼ 入力プロンプト例**
> あなたはスマートシティのデータモデリング専門家です。
> 今から『01_地域サービスデータモデル_作成ガイドライン.md』を読み込ませます。まずはこのガイドラインの全体像と『2. 実装プロセス』の流れを読み込んで、理解した旨だけを返答して待機してください。
> その後、私から『STEP ○の処理を開始してください』と指示を出しますので、そのSTEPの手順に厳密に従って対話形式で作業を進めていきましょう。

### STEP 1：既存ドキュメントの確認
- 既存の`地域サービス・データモデル・ガイドブック.md`を生成AIにて読み込み、各章構成を認識すること。
- 該当は3章(# 3)、4章(# 4)、5章(# 5)、6章(# 6)とする。`# 3`、`# 4`、`# 5`、`# 6`をチャンク化(Chunking)し、`##`の単位で読み込めるようにすること。

### STEP 2：データモデルの抽出
**目的: 各ドメインのデータモデルの抽出と構造化**
- `地域サービス・データモデル・ガイドブック.md`を読み込み、各データモデルを構造化された表形式で抽出すること。
- AIの一括処理によるコンテキストロストや抽出漏れを防ぐため、本ステップは担当者の指示により分割して実行（STEP 2-1 〜 2-3）する。

**【STEP 2-1】ファイルの読み込みとチャンク化**
- **担当者指示**: 「STEP 2-1を開始してください。3章と4章を読み込み、章節単位で構造を把握して待機してください」
- **AIの処理**: 3章(# 3)および4章(# 4)を対象とし、`##` または `###` 単位でチャンク化して構造を把握し、完了の旨だけを返答して待機する。

**【STEP 2-2】ドメイン（章・節）ごとの抽出実行**
- **担当者指示**: 「STEP 2-2として、`## 4.1`（章番号指定）の抽出を実行してください」
- **AIの処理**: 指定された範囲について以下の詳細ルールで抽出し、AIのメモリ上に保持する（※この段階ではCSVを出力しない）。

    1. **抽出する内容**:
       - `# 3 全てのデータモデルの共通事項`: 全てのデータモデルで共通に使われるデータモデルとして抽出。
       - `# 4 実装データモデル`: `#### a)データモデル` で始まる表を基本として抽出する。
         - **基本モデルと派生モデルの判定**:
           - `##` にひとつのデータモデルしかない場合は、それが「基本形」となる。
           - `##` に複数のデータモデルある場合は、`### 1) 基本形` に記載されるものを「基本形」とする。
           - ドキュメントの説明文で付加する等の記載があるものは「派生モデル」とする。
           - 派生モデルはどの基本モデルに紐づくかも抽出し、クラスのリレーション関係（親クラス）を特定する。
    2. **入力パターンの認識**: 以下の表パターン（Pattern 1～5）が想定されるため、柔軟に認識すること。
       - Pattern 1: `必須`, `データ項目`, `説明`
       - Pattern 2: `データ項目`, `Schema.org`, `説明` 
       - Pattern 3: `データ項目`, `Smart Data Models`, `説明`
       - Pattern 4: `必須`, `データ項目`, `Schema.org`, `説明`
       - Pattern 5: `データ項目`, `説明`
    3. **データ変換（カラムの引き継ぎ）**:
       - 入力と出力でヘッダーが同一のものはそのまま引き継ぐ。
       - 入力側の `データ項目` は、出力側の `日本語論理名` に引き継ぐ。
       - 入力側の `Schema.org` は、出力側の `英語論理名` と `Schema.org` の両方に引き継ぐ。
       - 入力側の `Smart Data Models` は、出力側の `英語論理名` と `Smart Data Models` の両方に引き継ぐ。
    4. **【重要】ハルシネーション防止**: **ガイドブックの表内に存在しない「架空のデータ項目（行）」をAIが独自に推測して追加することは厳禁とする。** 属性の抽出は、表内に記載されたテキストのみに限定すること。

**【STEP 2-3】全件結合CSVの出力**
- **担当者指示**: 「全ドメインの抽出が完了しました。STEP 2-3としてCSVを出力してください」
- **AIの処理**: 保持している全データを結合し、以下のヘッダーとルールに従ってCSVコードブロックのみを一度だけ出力する。解説は不要。
    - **出力CSV (`地域サービス_データモデル抽出.csv`) のヘッダー**:
      `RowID`, `章番号`, `分類`, `親クラス`, `細分`, `必須`, `日本語論理名`, `英語論理名`,`プレフィックス`,`多重度`, `データ型`, `正規パターン`, `説明`, `単位`, `Smart Data Models`, `Schema.org`, `3D都市モデル`,`GIF`,`IMI`, `関連クラス`
    - **各カラムの格納ルール**:
      - `RowID`, `データ型`, `正規パターン`, `3D都市モデル`,`単位` の中身は空 `null` とすること。
      - `章番号`: `## 4.3.1` などの採番部分を格納（例：`4.3.1`）。
      - `分類`: `##` の番号の後に続く項目名を格納（例：`## 4.1 土地` では `土地` を格納）。
      - `親クラス`: 派生モデルの場合、本文中に「〇〇の基本モデルを利用」や「[〇〇](#...)を付加して利用」といった**明示的な参照先**があるかを確認し、その**一段階上の直接的な親クラス名のみ**を格納する。文化財のように複数参照がある場合はセミコロン区切り（例：`建物; 施設`）とする。自身が基本形の場合は空欄またはルート名とする。
      - `細分`: `###` の番号の後に続く項目名を格納（例：`### 9) 公園` では `公園`。`### 1) 基本形` では `基本形`）。
      - `関連クラス`: `#### a)データモデル` の説明欄において `[ ](# )` といったリンクがある場合に、`(# )` で囲まれたリンク先を記載する（例：`[駐車場料金一覧](#料金一覧情報型)` の場合、`料金一覧情報型` を格納）。

### STEP 3：日本語論理名の品質確認とクレンジング
**目的: 命名規則への準拠、重複の排除、およびメタデータ（単位・補足情報）の分離・正規化**

1. **命名規則の適用**
   - `02_地域サービス_命名ガイドライン.md` を読み込ませ、以下のチェック基準として使用する。

2. **入力と処理単位（ターン制の徹底）**
   - STEP 2で出力した `地域サービス_データモデル抽出.csv` を読み込ませる。
   - AIの一括処理によるパンクを防ぐため、**必ず `分類` ごとに1つずつチャンク化して処理し、担当者の承認（確定）を得てから次の分類へ進む「ターン制」**で実行すること。
   - **▼ 担当者プロンプト例（対話の進め方）**:
     - **開始時**: 「STEP 3を開始します。まずは最初の分類の修正案を提示してください」
     - **承認・次へ**: 「その修正案で完璧です。確定して、次の分類に進んでください」
     - **微修正の指示**: 「『〇〇』の項目は分割せず、そのままにして案を出し直してください」

3. **個別確認とクレンジング（分類ごとの対話）**
   AIは指定された分類について以下の観点でチェックし、**表形式で「修正前」「修正案」「修正理由」を提示**して担当者の確認を待つこと。
   - **ガイドライン準拠**: 禁止文字や命名規則への抵触がないか。
   - **原子性（アトミック）の確保**: 複合項目（例：「名称と住所」）が含まれている場合は、行の分割を提案する。
   - **単位・補足情報の分離（メタデータの退避）**: 
    `日本語論理名` または `説明` カラムの文字列に単位（例：「(m)」「(人)」等）や補足情報（括弧書きの注釈など）が含まれている場合、以下の処理案を提示すること。
     1. **論理名の純化**: 元の文字列から単位や補足情報を除去し、純粋な論理名のみにする。
     2. **単位の移動**: 抽出した「単位」は、専用の `単位` カラムへ格納する。
     3. **補足情報の退避**: 抽出した「補足情報」は、`説明` カラムの文末に追記する。

4. **全体整合性の確認（全分類の完了後）**
   - すべての分類の個別クレンジングが完了した後、担当者の指示により**全データを横断したチェック**を実行する。
   - **同義語・同意語**: 意味が同じで名称が異なる項目の統一案を提示。
   - **重複**: 意味が異なり名称が重複している項目（※別の分類で同じ名前が使われているが意味が違うケース等）の修正案を提示。
   - 全ての修正を担当者が確定した後、最終結果を全件結合済みの `地域サービス_データモデル.csv` として出力し、上書き保存する。

### STEP 4：英語名の付与
**目的: 英語論理名の付与**
`地域サービス・データモデル・ガイドブック.md`の日本語論理名に対し英語名を付与し、英語論理名に格納する。

1. 命名規則
   - 英語名の付与は、`02_地域サービス_命名ガイドライン.md`の通りとする。
   - ただし、GIFのコアデータモデルにて英語名があらかじめ定められている場合は、GIFのコアデータモデルを優先とし、`05_コアデータモデル_一覧.csv`の通りとする。
2. 入力ファイルの読み込み
   - 入力ファイルとして、STEP 3で上書き修正された`地域サービス_データモデル抽出.csv`を読み込む。
   - `分類`ごとにチャンク化して、`3. GIFコアデータモデルの英語名の付与`および`4. 命名規則による英語名の付与`を実施できるようにすること。
3. GIFコアデータモデルの英語名の付与
   生成AIを使う必要性がない対応のため、生成AI以外の方法での実施を検討のこと。
   - 実施前に、使用する生成AIにプロンプトで実施する内容を指示し、`05_コアデータモデル_一覧.csv`を読み込ませる。
   - `分類`ごとにチャンク化して、実施すること。
   - 読み込んだ`地域サービス_データモデル抽出.csv`の`日本語論理名`と`05_コアデータモデル_一覧.csv`の`項目名`が一致した場合、`地域サービス_データモデル.csv`の`英語論理名`に、`05_コアデータモデル_一覧.csv`の`物理名_項目名(英語)`を格納する。
   - 更新された結果をCSV形式のコードブロックとして出力させ、担当者が手動でローカルの地域サービス_データモデル.csvに上書き保存すること。（※共通ルールに従い、全チャンクの処理完了後に一括出力・保存すること）
4. 命名規則による英語名の付与
   - 実施前に、使用する生成AIにプロンプトで実施する内容を指示し、`02_地域サービス_命名ガイドライン.md`を読み込ませる。
   - `分類`ごとにチャンク化して、実施すること。
   - 読み込んだ`地域サービス_データモデル抽出.csv`の`日本語論理名`をもとに、命名規則に従い、英語名を付与する。
   - ただし、`英語論理名`に格納されているデータがある場合は、新たに英語名の付与は行わない。
   - 付与された英語名を`英語論理名`に格納した状態で、生成AIにCSV形式のコードブロックを出力させる。
   - 担当者はそれを手動でコピーし、ローカルの地域サービス_データモデル.csvに上書き保存すること。（※共通ルールに従い、全チャンクの処理完了後に一括出力・保存すること）
5. 英語名の揺れ・整合性の一括確認
   - 全分類のチャンク処理が完了し、1つに結合された`地域サービス_データモデル.csv`全体を使用する。
   - 生成AIに全件データを読み込ませ、以下の観点で英語論理名の表記揺れや不整合を抽出し、修正を提案させる。
     - **同義語の揺れ**: 類似する日本語論理名に対して、異なる英単語が使われていないか（例：「名称」に対し `name` と `title` が混在していないか等）。
     - **フォーマットの崩れ**: キャメルケースなどの指定された命名規則から外れているものがないか。
   - 担当者が修正提案を確認して確定させた後、生成AIに最終的なCSV形式のコードブロックを出力させる。
   - 担当者はそれを手動でコピーし、ローカルの`地域サービス_データモデル.csv`に上書き保存すること。

### STEP 5：データ型の定義

   - 論理モデルのデータ型は、`03_地域サービス_データ型式ガイドライン.md`を参照する。

2. 入力ファイルの読み込み
   - 入力ファイルとして、STEP 4で上書き修正された`地域サービス_データモデル抽出.csv`を読み込む。
   - `分類`ごとにチャンク化して、`3. データ型の付与`を実施できるようにすること。

   - 担当者はそれを手動でコピーし、ローカルの`地域サービス_データモデル.csv`に上書き保存すること。

### STEP 6：外部標準モデルとの整合確認
**目的: 外部標準モデル（Schema.org、Smart Data Models、3D都市モデル）の既存マッピングの整理・補完と、公式仕様に基づく正確性確認**
`地域サービス・データモデル・ガイドブック.md`に記載されているマッピング情報をベースにしつつ、生成AIに公式仕様を考慮させた上でプロパティを推論・補完させる。その際、ガイドブック末尾のリンク集を活用して推論の根拠となるURLを提示させ、正確性を担保する。

1. 入力ファイルの読み込み
   - 入力ファイルとして、STEP 5まで完了し1つに結合された`地域サービス_データモデル.csv`を読み込む。
   - 合わせて、マッピングの前提となる`地域サービス・データモデル・ガイドブック.md`を生成AIに読み込ませる。（※特に末尾の脚注リンク集も正しく認識させること）
   - `分類`ごとにチャンク化して実施すること。
2. 既存マッピングの確認とクラス定義の抽出
   - ガイドブックの各分類にある `b)参照元データ` に記載された各外部標準のクラス名（例: `Building`, `urf:UrbanFacility`, `Park` など）を抽出し、生成AIに認識させる。
   - STEP 2の段階で抽出されている `Schema.org`、`Smart Data Models` の既存値についても、本当に存在するか再評価の対象とする。
3. 公式仕様に基づくプロパティの推論・補完（Schema.org / Smart Data Models / PLATEAU）
   - 各カラムの空欄部分の推論、および既存値の妥当性チェックを行う。
   - **推論の制約**: 当てずっぽうに推論するのではなく、手順2で抽出した「対象クラス（またはその親クラス）」に実在するプロパティの中から最適なものを推論する。該当するものがない場合は無理に推論せず空欄とする。
   - **【重要】根拠URLの提示**: 生成AIは、ガイドブック末尾の脚注（例：`https://schema.org/` 等）をベースURLとして用い、推論したプロパティの公式ドキュメントURL（例：`https://schema.org/address`）をセットでテキスト出力（提案）すること。
4. 担当者による裏付け確認と一括保存
   - 担当者は、生成AIが提案したマッピング結果と「根拠URL」をクリックして公式ドキュメントを開き、そのプロパティが本当に実在するか、意味が合致しているかを必ず目視確認する。
   - 担当者が確認・修正して確定させた後、URL情報を除いた最終的なCSV形式のコードブロックを生成AIに出力させる。
   - 担当者はそれを手動でコピーし、ローカルの`地域サービス_データモデル.csv`に上書き保存すること。（※共通ルールに従い、全チャンクの処理完了後に一括出力・保存すること）

### STEP 7. 多重度の定義ルール
各属性が保持できるデータ数の範囲を示す「多重度（Multiplicity）」は、原則としてデータモデルにおける**必須フラグの有無**と**最大数（Cardinality）**の組み合わせに基づき、以下のルールに従って定義する。

* **多重度定義の基本ルール**
  * **`1`** : 必須・単一（必須項目であり、かつ最大数が `1` のもの）
  * **`1..*`** : 必須・複数可（必須項目であり、かつ最大数が `n` のもの）
  * **`0..1`** : 任意・単一（必須フラグがなく、かつ最大数が `1` のもの）
  * **`0..*`** : 任意・複数可（必須フラグがなく、かつ最大数が `n` のもの）

* **必須パターン（Mandatory Pattern）が存在する項目の実務的運用**
  * コアデータモデルの仕様上、複数の必須パターン（MP01, MP02等）によって「必須」と「任意」が変動する項目が存在する。
  * これらについては、データモデル（箱）の共通化と設計の確実性を優先し、**いずれか一つのパターンでも必須となる場合は、一律で「必須（必）」として定義する。**
  * これに伴い、多重度の表記も安全側の設計（実装漏れ防止）を採用し、対象項目の最大数（Cardinality）に応じて **`1`** または **`1..*`** を適用することとする。
  * ※条件分岐によるバリデーション等の複雑な制御は、データモデルの基本定義からは切り離し、後続のシステム実装レイヤーまたは個別バリデーションルール側へ委譲する。

* **クラス宣言行（空行・ヘッダー行）の扱い**
  * プロパティを持たない「クラスそのものを定義している行」やセクション区切り行については、多重度カラムは「空欄（null）」とする。

### STEP 8：コード定義（値リスト）の抽出
**目的: 各属性に付随する選択肢（統制語彙）を抽出し、マスターデータとして整理する**
`地域サービス・データモデル・ガイドブック.md` の各章にある「c) データ項目に選択肢があるときの候補」や「5. コード体系」から、具体的なコード値と名称のリストを抽出する。
**なお、本ステップは後続のロジックによる詳細なクリーンアップを前提とし、ガイドブックからの網羅的な拾い出しを目的とした「前処理」として実施する。**

1. **入力ファイルの読み込み**
   - `地域サービス・データモデル・ガイドブック.md` および `06_コード整備ガイドラインmd` を生成AIに読み込ませる。
   - `分類`（章単位）ごとにチャンク化して実施すること。

2. **コード情報の抽出項目**
   各データモデルの「c) 候補」や「第5章」から、以下の情報を漏れなく抽出する。
   - **対象項目名**: どの属性（例：医療機関区分）のコードリストか。
   - **コード値**: 数値や英数字のID。記載がない場合は空欄または連番推論とする。
   - **コード名称**: 日本語のラベル（優先語）。
   - **定義説明**: その値が何を指すかの具体的な解説。
   - **参照元**: 図表の出典や、第5章のセクション名、外部URL等。

3. **正規化と性質の判定（ガイドラインの適用）**
   抽出データに対し、`06_コード整備ガイドライン.md` に基づき以下の処理（前処理）を行う。
   - **表記の正規化**: 
     - 名称は原則**全角**、英数字は**半角**に統一する。
     - 外来語末尾の**長音（ー）は省略せず**に記載する（例：コンピューター）。
   - **コードの性質の判定**: 
     - そのコード体系が「有意」「無意」「組み合わせ」のいずれに該当するかを推論して付与する。

4. **CSV形式での出力**
   - 抽出結果を以下のカラム構成でコードブロック出力させる。
     - `分類`, `対象項目名`, `コード値`, `コード名称`, `コードの性質`, `定義説明`, `参照元`
   - 担当者はこれをコピーし、ローカルの `地域サービス_コード定義.csv` に保存すること。
   - ※共通ルールに従い、全件の処理完了後に一括出力・保存すること。
