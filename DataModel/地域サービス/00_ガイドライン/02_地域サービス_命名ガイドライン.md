# 地域サービス_命名ガイドライン

## 1. 目的
本ガイドラインは、スマートシティのデータモデルを定める、実装データモデル・地域サービス・データモデル・ガイドブックに記載されるデータモデルの相互運用性を確保するため、データの命名規則を定めるものである。

## 2. 命名ガイドライン (ISO/IEC 11179-5 準拠と実務的省略)

### 2.1 命名の公式
データ要素名は **lowerCamelCase（先頭小文字のキャメルケース）** を採用する。
基本構造は **「オブジェクト語」＋「プロパティ語」＋「表現用語」** とするが、**可読性を優先し、冗長な表現用語は省略する。**
- **日本語名**: `[オブジェクト名][プロパティ名][表現用語]`
- **英語名**: `[object][Property][Representation]` (lowerCamelCase)
- ただし、日本語名の場合、語順は日本語の自然さを優先して入れ替えてよい。: `[プロパティ名][オブジェクト名][表現用語]`

### 2.2 命名の基本原則
1. **標準的略語の採用**: 
   - IT用語、ドメイン用語として広く定着している略語は、可読性向上のために使用を推奨する。
   - 許容される略語の例:
     - IT標準: Id, Uri, Mac, Ip, Db, Api, Gps, Json, Xml
     - 一般: Max (Maximum), Min (Minimum), Avg (Average), Tel (Telephone), Msg (Message)
2. **外部標準との整合**
   - 外部標準とキーとして連携する固有項目（例: localGovernmentCode）については、マッピングミスを防ぐため、原則として外部標準の綴りに合わせる（無理に略さない）。
   - ただし、プロジェクト内の辞書定義があれば短縮形も可とする。
3. **接続詞・前置詞の扱い**:
   - 英語の慣用表現として一般的、または外部標準で採用されている場合は、`of`, `to`, `from` 等の使用を許容する。
   - 例: `birthDate` だけでなく `dateOfBirth` も可とする。

### 2.3 構成要素の定義
1. **オブジェクト語 (Object Class Term)**
   - データが属する対象。
   - 例：`Facility` (施設), `Event` (イベント), `Parking` (駐車場)
2. **プロパティ語 (Property Term)**
   - オブジェクトの具体的な性質。
   - 例：`Capacity` (収容人数), `Condition` (状況), `Availability` (利用可否)
3. **表現用語 (Representation Term)**
   - データの型や形式を示す末尾語。記載の有無は**本ガイドラインの表現用語の適用・省略ルール**による。
   - 例：`Identifier` (識別子), `Count` (数), `Amount` (量), `DateTime` (日時), `Text` (説明文), `Code` (区分値)

### 2.4 表現用語の適用・省略ルール
論理データ型ごとの接尾辞:Suffix（表現用語）適用ルールは以下の通り。
このルールは英語名の場合の記載とする。

| 論理データ型 | 基本サフィックス | **省略・統合ルール ** | 良い例 (Good) | 悪い例/冗長 (Bad) |
| :--- | :--- | :--- | :--- | :--- |
| **コード(文字列)** | `Code` | プロパティ名が「〜コード」の場合は重複させない。 | `localGovernmentCode`<br>`poiCode` | `localGovCodeCode`<br>`poiCodeCode` |
| **ID(UUID)** | `Id` | **必須**。省略しない。キャメルケースに従い `Id` とする。 | `facilityId` | `facility` |
| **文字列** | `Text` | **原則省略**。`note`や`address`など単語自体で意味が通じる場合は付けない。 | `note`<br>`address` | `noteText`<br>`addressText` |
| **文字列(全角)** | `Name` | プロパティ名が「〜名/名称」なら、それをそのまま使う（二重にしない）。 | `facilityName` | `facilityNameName`<br>`facilityNameText` |
| **文字列(半角)** | `Text` | **「電話番号(Number)」や「メール(Address)」など、単語に型が含まれる場合は省略。** | `telephoneNumber`<br>`mailAddress` | `telephoneNumberText`<br>`mailAddressText` |
| **文字列(半角英数)** | `Text` | 同上。 | `authToken` | `authTokenText` |
| **URI** | `URI` | **必須**。URL/URIであることが重要なため残す。 | `imageURI` | `image` |
| **数値(整数)** | `Count` | **推奨**。「数」であることを明確にするため付ける。 | `participantCount` | `participant` (人かどうかわからない) |
| **数値(実数)** | `Value` / `Measure` | 単位や測定値であることが自明なら省略可だが、物理量(`Measure`)は残すのが無難。 | `areaMeasure` | `area` (広さの量) |
| **日時** | `DateTime` | **推奨**。日付(`Date`)と区別するため付ける。 | `startDateTime` | `start` |
| **日付** | `Date` | **推奨**。 | `registrationDate` | `registration` |
| **論理値** | `Indicator` | `is...` や `has...` で始まる場合は省略可。 | `isOpen`<br>`hasWifi` | `isOpenIndicator` |

### 2.5 状態・状況の使い分け基準（語彙統制）
日本語における「状況」「状態」などの曖昧さを排除するため、以下の対応ルールを適用する。

| 英語サフィックス | 日本語統一名称 | 定義・使い分け | データ例 |
| :--- | :--- | :--- | :--- |
| **`Status`** | **状態 / 有無** | **ライフサイクル、またはGIF準拠の「有無」。**<br>※GIF等の外部標準が「有無(Presence)」を`Status`と定義している場合はそれに従う。 | 開催状態 (`eventStatus`)<br>駐車場有無 (`parkingStatus`) |
| **`Condition`** | **状況** | **物理的・環境的な良し悪しや様子。**<br>（例：良好/破損、清潔/不潔、安全/危険） | 衛生状況 (`hygieneCondition`) |
| **`Availability`** | **可否** | **利用できるか、提供できるか。**<br>※コード値は**GIFの「有無コード」(1:有, 2:無)** を「1:可, 2:否」と読み替えて準用する。 | トイレ利用可否 (`toiletAvailability`)<br>充電可否 (`chargingAvailability`) |
| **`Category`** | **区分** | **制度、運用、大枠の領域などによる「仕切り・枠組み（区切り）」としての分類。**<br>※同一ドメインに大分類・小分類の階層構造がある場合は**大分類**に用いる。 | イベント区分 (`eventCategory`) |
| **`Type`** | **種別 / 形式** | **物自体の性質、構造、形状、システム上の型などの違いによる「種類・型」。**<br>※同一ドメインに大分類・小分類の階層構造がある場合は**小分類（細分）**に用いる。 | 施設種別 (`facilityType`) (※図書館、体育館などの種類)<br>燃料種別 (`fuelType`) |
| **`Indicator`** | **有無 (フラグ)** | **単純な二値（True/False）の有無。**<br>※3値以上のコード値（有/無/不明）で管理したい場合は `Status` または `Code` を検討する。 | 駐車場有無 (`hasParking`)<br>Wi-Fi有無 (`hasWifi`) |

### 2.6 命名の具体例（Before / After）

| 日本語名 | 厳密な11179 (Bad) | **本ガイドライン (Good)** | 理由 |
| :--- | :--- | :--- | :--- |
| 施設電話番号 | `facilityTelephoneNumberText` | **`facilityTelephoneNumber`** | `Number`で文字列(数字列)とわかるため。 |
| 施設名称 | `facilityNameText` | **`facilityName`** | `Name`で文字列とわかるため。 |
| 住所 | `addressText` | **`address`** | `address`は文字列に決まっているため。 |
| 参加者数 | `participantCount` | **`participantCount`** | 単に`participant`だと「参加者オブジェクト」か「数」か紛らわしいため残す。 |
| 利用可能フラグ | `availableIndicator` | **`isAvailable`** | `is` + 形容詞 でBooleanとわかるため。 |

### 2.7 命名公式の具体的な適用例

| 日本語名（論理名） | 英語名（物理名） | オブジェクト | プロパティ | 表現用語 |
| :--- | :--- | :--- | :--- | :--- |
| 施設収容人数 | `facilityCapacityCount` | 施設 | 収容 | 数 |
| 駐車場利用可能台数 | `parkingAvailableCount` | 駐車場 | 利用可能 | 数 |
| イベント開催状態コード | `eventStatusCode` | イベント | 開催状態 | コード |
| 予約申込日時 | `reservationDateTime` | 予約 | 申込 | 日時 |
