# 施設管理_クラス図作成ガイドライン

## 1. 目的
本ガイドラインは、行政の施設管理データモデルについて、入力Excel、データモデルCSV、クラス図および定義書の内容を一致させ、相互運用性を確保するための設計原則を定めるものである。

## 2. クラス図作成ガイドライン

### 2.1 識別子の扱い
- **Primary ID（PK）**: 入力Excelの `PK` と対応する正本のPKを、独立したレコードとして管理するクラスの先頭属性として保持する。英語名は原則として `[objectName]Id` とする（例：`facilityId`）。値型や抽象的な共通基底クラスには独立したPKを一律に要求しない。
- **Foreign ID（FK）**: 入力Excelの `FK` を属性として保持し、参照先のクラス、参照先属性および多重度を定義する。クラス図ではFK属性を記載したうえで、クラス間の関係線も引く。
- PK/FKはデータモデルCSV、クラス図および定義書に同じ内容を記載し、変換時に削除しない。

### 2.2 単位の扱い
- 物理量（Measure）を扱うプロパティには、単位名称、単位記号および準拠規格または出典を設定する。
- 単位は数値に埋め込まず、データモデルCSVおよび定義書の独立した項目として管理する。
- クラス図では、属性の直後にMermaidコメントとして単位を記載する。計数値についても必要に応じて人、件、台、棟などの表示用単位を記載する。
- 描画されたクラス図には単位を表示しない。単位の正本はデータモデルCSVまたは単位一覧とし、HTML定義書で確認できるようにする。AIや処理プログラムは正本またはMermaidソースのコメントから単位を取得する。
- コメントは正本から生成し、単位を変更するときは正本を更新して再生成する。単位が図に表示されないことを欠落や検証不合格として扱わない。

### 2.3 共通クラスの適用
- 入力項目の棚卸し後に、複数クラスで意味と制約が一致する属性または値型を共通クラスの候補とする。
- 全クラスへ機械的に同じ基底クラスを適用せず、継承、コンポジションまたは関連のどれが適切かを確認する。
- 共通属性の定義には、**GIF（政府相互運用性フレームワーク）**のコアデータモデルや標準メタデータを積極的に採用し、国や他システムとの相互運用性を確保する。
- 共通化した場合も、入力Excelの元項目、PK/FK、必須区分および定義との対応関係を保持する。
- 新設するクラス・属性は、由来区分、追加理由および出典・設計判断を正本データに記録する。元Excelはインプット原本として保持し、新設要素に架空の元行番号を付与しない。
- 共通属性の候補例：`識別子 / identifier`、`名称 / name`、`作成日時 / createdDateTime`、`更新日時 / modifiedDateTime` 等

### 2.4 プレフィックスの付与
- クラスおよびプロパティには原則として `pd:`、コードリストおよび統制語彙には原則として `pcd:` を付与する。
- 外部標準の要素を直接参照する場合は、その標準で定義されたプレフィックスを使用する。
- Mermaidの内部クラス識別子にはコロンを含めず、表示ラベルおよび属性の英語名にプレフィックスを記載する。
- 入力Excelの物理テーブル名に含まれる `m_`、`t_` およびレコードID値の識別用プレフィックスは、名前空間プレフィックスとは区別する。

### 2.5 外部コードリストおよび統制語彙
- コード値または選択値を持つ属性について、適用可能な公的・標準的コードリストおよび統制語彙を確認する。
- 適用可能な標準が存在する場合は、その利用を前提とし、クラス図および定義書に参照先、管理主体、バージョンまたは適用時点を記録する。
- 標準が要件を満たさない場合は、標準との対応関係を記録したうえでプロジェクト固有コードを定義する。
- 外部コードリストや大規模な統制語彙は値を図中に展開せず、参照先を示すクラスまたは注記で表現する。
- 出典、管理主体、バージョン、ライセンス等の記述方法は、`05_施設管理_メタデータガイドライン.md` に従う。

### 2.6 ISO/IEC 11179 のその他関連パートの補足
- **Part 4 (定義の策定ルール)**: 「項目名」だけでなく、第三者が誤解しない「定義文」をセットで記述すること。
- **Part 6 (登録)**: 確定した項目に「管理番号」を振り、バージョニングを行うこと。

## 3. クラス図記述ルール（Mermaid出力 / UMLの考え方を適用）

本プロジェクトでは、正本データ一式からMermaid形式でクラス図を生成する。Enterprise Architect (EA) 等は必要に応じた連携先とし、利用を必須としない。以下の記法を標準とする。

### 3.1 クラスと属性の表記

クラスおよび属性には、以下の要素を定義する。「日本語論理名」と「英語論理名」を入力することで、論理名（英語）と論理名（日本語）の対応をツール上で管理する。なお、論理名（英語）は物理名として利用できる前提とする。

#### A. クラス (Class)
- **内部識別子**: Mermaidで参照するクラス識別子は、プレフィックスを除いた `UpperCamelCase` を基本とする（例：`Facility`）。異なる名前空間に同名クラスがある場合は、接頭辞等で一意化する。コロンは使用しない。正本で管理する恒久的な内部管理IDとは対応を保持する。
- **表示ラベル**: 日本語の論理クラス名とプレフィックス付き英語名を併記する（例：`施設 / pd:Facility`）。
- **EAでの管理**: 日本語論理名、英語論理名、名前空間プレフィックスおよび物理テーブル名を別項目として管理する。
- **ステレオタイプ**: クラスの性質を表す場合に付与。（例: `<<DataType>>`, `<<Enumeration>>`）

#### B. 属性 (Attribute)

記述フォーマット: `+ [キー区分] 日本語論理名 / プレフィックス付き英語論理名 : データ型 [多重度]`
EAツールへのインポートおよび視認性を両立するため、スラッシュ（/）区切りで両方を記述し、その後に正式なデータ型を添えること。

| 要素 | 可視性 | キー区分 | 名前と別名 | 型 | 多重度 | 単位 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **表記ルール** | 原則 `+` (Public) | `PK`、`FK`、または空欄 | `日本語論理名 / prefix:lowerCamelCase` | 定義済みの論理データ型（※半角カッコ不可） | `[1]`, `[0..1]`, `[0..*]` を明記 | 物理量または計数値に設定 |
| **記述例** | `+` | `FK` | `施設ID / pd:facilityId` | `ID（文字列）` | `[1]` | 空欄 |

EAでの入力・Mermaid出力イメージ:
- `+ PK 施設ID / pd:facilityId : ID（文字列） [1]`
- `+ 収容可能人数 / pd:capacityCount : 数値（整数） [0..1]`
- `  %% 単位:人`
※注意：Mermaidパーサーが関数（メソッド）と誤認するのを防ぐため、型表記に半角カッコ `()` は絶対に使用せず、**全角カッコ `（）`** を使用すること。

### 3.2 関係線の使い分け基準
関係性は「参照」か「所有」かの2種類で厳密に使い分けること。迷った場合は「関連」を選択する。

| 種類 | 記号 (Mermaid) | 適用ルール (ライフサイクル基準) |
| :--- | :---: | :--- |
| **関連 (Association)** | `-->` | **「参照」**。互いに独立しており、IDを知っているだけの関係。<br>親が削除されても子は残る。<br>（例：避難所が自治体マスターを参照する） |
| **コンポジション (Composition)** | `*-->` | **「所有」**。親が削除されたら子も同時に削除される**強い親子関係（運命共同体）**。<br>子は親の一部であり、単独では存在し得ない。<br>（例：避難所が共通型である住所を所有する） |
| **汎化 (Generalization)** | `<|--` | **「継承」**。共通クラス（`AbstractSmartCityBase`等）を継承する場合に使用。 |

### 3.3 多重度 (Multiplicity) の定義
属性と関連・コンポジションの両端には、正本で定義された多重度を明記する。汎化には多重度を付与しない。

入力Excelの必須区分は、単一値属性について `◎` を `[1]`、`○` を `[0..1]` に変換する。複数値およびリレーション反対側の多重度は、最大数、業務ルールおよび参照関係を別途確認して設定する。

| 表記 | 意味 | 備考 |
| :--- | :---: | :--- |
| **`"1"`** | 必須 (Exactly One) | NULL不可。必ず1つ存在する。 |
| **`"0..1"`** | 任意 (Zero or One) | NULL可。存在しない場合がある。 |
| **`"0..*"`** または **`"*"`** | 複数 (Zero or More) | リスト。0件の場合もある。 |
| **`"1..*"`** | 1以上 (One or More) | 少なくとも1件は必須。 |

## 4. クラス図の作成手順

### 4.1 事前準備（入力ファイルの読み込み）
クラス図の作成にあたり、以下のファイルを使用する。
1. **公共施設with防災・ファシマネ属性.xlsx**: 元の項目名、PK/FK、必須区分、データ形式および説明を保持する一次情報。
2. **施設管理データモデル.csv**: 一次情報を確認・正規化し、論理名、英語名、プレフィックス、型、キー、多重度、単位および参照先を含む正本データ。
3. **施設管理コード定義.csv**: 各項目が参照する外部コードリスト、統制語彙およびプロジェクト固有コードの定義データ。
4. **関連する正本CSV**: 工程6で分割管理すると決めたクラス定義、リレーション定義、単位一覧、元項目対応等。

クラス図は、入力Excelとの対応および新設要素の根拠が確認済みの「施設管理データモデル.csv」を中心とする正本データ一式を直接の生成元とする。各CSVの結合には確定した内部管理ID・参照規則を使用する。

### 4.2 クラス図作成の基本方針
- **ドメイン単位の出力**: 巨大な図の一括生成は避け、必ず「分類（ドメイン）」単位、またはさらに細分化した「サブカテゴリ」単位で出力すること。

- **対象ドメインの特定と分割戦略**:
  生成AIは、施設管理データモデルCSVの分類、物理テーブル名および参照関係に基づき、以下を基本単位として図を作成する。
  - **全体関連図**: クラス、PK/FKおよび主要な関係だけを示し、属性の詳細は省略する。
  - **施設基本図**: 施設基本マスタと、住所、連絡先、アクセシビリティ等の共通クラス候補を示す。
  - **設備図**: 設備マスタ、設備コードおよび施設との関係を示す。
  - **防災図**: 防災拠点、防災・避難状況履歴および施設との関係を示す。
  - **ファシリティマネジメント図**: 収支・コスト、利用状況・稼働、点検・修繕等の履歴クラスと施設との関係を示す。
  - 図が大きくなる場合は、分類またはサブカテゴリ単位に分割し、共通クラスを必要な範囲だけ再掲する。

### 4.3 属性およびリレーションの定義ルール

生成AIは、出力するクラス図において以下のUML記法および設計規則を厳守すること。

- **属性の表記形式**: `+ [キー区分] 日本語論理名 / プレフィックス付き英語論理名 : データ型 [多重度]` 形式で記述する。型、キー、多重度およびプレフィックスの脱落は厳禁とする。
- **共通クラスの適用**: 共通クラスの検討結果に基づき、継承する場合は汎化関係を明示する。共通クラスを適用しないクラスへ機械的に継承関係を追加しない。
- **識別子（ID）の処理**:
    - Primary ID : 正本でPKを定義したクラスでは先頭属性として配置し、`PK` を明記する。入力ExcelのPKとの対応を保持し、値型・抽象クラスには独立したPKを追加しない。英語名は原則として `[objectName]Id` とする。
    - 外部参照ID/コード（守備範囲外）: 「全国地方公共団体コード」「町字ID」「郵便番号」「座標参照系コード」など、システム外部のマスタに依存する項目は属性として保持し、標準的なコードリストまたは統制語彙の有無を確認する。外部参照先を図中のクラスとして描かない場合は、定義書に参照先、管理主体およびバージョンまたは適用時点を記載する。
- **Foreign ID（他クラス参照）の処理**:
     - 本モデル内で定義されている他クラスを参照する場合は、FK属性を属性リストに残し、`FK` を明記する。
     - FK属性には参照先クラスと参照先PKを定義し、クラス間にも多重度付きの関連線を引く。関係線のラベルには、対応するFK属性名を記載する。
     - 関係線は、3.2項のライフサイクル基準に従って、関連（`-->`）またはコンポジション（`*-->`）を選択する。
     - 「住所」「連絡先」「アクセシビリティ」「画像」などの共通型クラスも、一律にコンポジションとはせず、ID参照か値の内包かを確認して関係種別を決定する。
- **単位の処理**:
    - データモデルCSVの単位欄に値がある属性は、属性の直後に独立したMermaidコメントとして `%% 単位:単位記号または単位名称` を記載する。
- **コードリストおよび統制語彙の処理**:
    - コード属性には参照するコードリストまたは統制語彙の識別子を設定する。
    - 外部標準を利用する場合は、その標準を優先し、プロジェクト固有の列挙型として重複定義しない。
    - 小規模なプロジェクト固有コードのみ、必要に応じて `<<Enumeration>>` として図中に展開する。
- **多言語属性の集約ルール**:
    - 名称・カナ・英字表記等の集約は工程5の共通クラス設計で判断し、元項目との対応、各項目の意味・必須区分、採用する型を正本に記録する。英字表記が英訳かローマ字表記かも確認する。
    - クラス図は正本の構造をそのまま反映する。名前のサフィックスだけを根拠に、図の生成時に属性を自動統合・削除しない。
- **リレーションの多重度表記**:
    - 関係線の多重度は、接続名（ラベル）の中に埋め込まず、必ずクラス名の直後にダブルクォーテーションで囲んで記述（例：`住所_Address "1" *--> "0..*" 多言語文字列型_MultilingualString`）し、UML標準規格に準拠させること。

### 4.4 クラス図（Mermaid形式）の出力と運用

1. **Mermaid記法による出力**
   生成AIに、Markdown上でプレビュー可能なMermaid記法のコードブロック（```mermaid ~ ```）を出力させる。
   - **自動ソート・メソッド化エラー対策（最重要）**: クラスの `{}` 内に人間用の見出し（★表記やセクション区切り文字）を直接記述すると、Mermaidの自動ソート仕様により表示が崩れ、さらに半角カッコ `()` が混入するとメソッド（関数）として誤認識される原因となる。そのため、人間用のカテゴリ分けや見出しは、図の属性欄には入れず、ソースコード上のコメントアウト（`%%`）としてのみ記述すること。また、型表記のカッコは必ず全角 `（）` とすること。
   - **プレフィックスの表示ルール**: Mermaidの内部クラス識別子にはコロンを含めない。`class Facility["施設 / pd:Facility"]` のように表示ラベルへプレフィックス付き名称を記載し、属性にも `pd:facilityId` のようにプレフィックスを付与する。
   - **PK/FKの表示ルール**: 属性名の前に `PK` または `FK` を通常の文字列として記載する。FKについては属性表示と関係線を併用する。
   - **物理量（単位）の記述ルール**: 属性に対応する単位（人、m2、台など）は、属性と同じ行の後ろ（インライン）には記述せず、必ず**「対象属性の直後の行に、インデントを下げて独立したコメント行（`%% 単位:〇〇`）として記述」**すること。
   - **Namespaceによる構造化**: 図の肥大化を防ぎ視認性を高めるため、メインクラス以外の「共通クラス（Components）」や「コード・リスト定義クラス（Enumeration）」を出力する際は、それぞれ `namespace 共通クラス { ... }` や `namespace コード定義 { ... }` などの名前空間構文を用いてグループ化すること。
   - **コード定義の反映**: 外部コードリストまたは統制語彙は参照先を示し、値を重複定義しない。プロジェクト固有コードは、必要に応じて `class クラス名 <<Enumeration>>` として図中に描き、対象クラスから関連線を引くこと。
   - **肥大化防止ルール**: コードリストの選択肢（値）が5つ以上ある、または膨大な場合は、Mermaid内にすべての値を書き込まず、クラス内に「%% ※詳細はコードマスタ参照」とコメントを記述し、図の肥大化とレンダリングエラーを防止すること。選択肢が4つ以下の場合は、`符号 : 日本語ラベル` の形式で列挙してよい。

   * **出力イメージ（施設共通モデルの基本構造）**:
     以下は記法の例であり、元Excelから確定した施設管理モデルではない。住所を独立レコードとして管理し、名称を共通型に集約する判断が正本に記録された場合の例とする。英字表記はここでは英語訳を仮定している。
     ```mermaid
     classDiagram
       direction TB

        class AbstractFacilityManagementBase["施設管理共通基底 / pd:AbstractFacilityManagementBase"] {
            + 作成日時 / pd:createdDateTime : 日時 [0..1]
            + 更新日時 / pd:modifiedDateTime : 日時 [0..1]
        }

        class Facility["施設 / pd:Facility"] {
          + PK 施設ID / pd:facilityId : ID（文字列） [1]
          + FK 住所ID / pd:addressId : ID（文字列） [1]
          + 施設種別 / pd:facilityType : コード（文字列） [1]
          + 名称 / pd:name : 多言語文字列型 [1]
          + 説明 / pd:description : 文字列 [1]
          + 収容人数 / pd:capacityCount : 数値（整数） [0..1]
            %% 単位:人
        }

        namespace 共通クラス {
            class Address["住所 / pd:Address"] {
                + PK 住所ID / pd:addressId : ID（文字列） [1]
            }

            class MultilingualString["多言語文字列型 / pd:MultilingualString"] {
                <<DataType>>
                + 日本語 / pd:ja : 文字列 [1]
                + カナ / pd:kana : 文字列 [0..1]
                + 英字 / pd:en : 文字列（半角） [0..1]
            }
        }

        namespace コード定義 {
            class FacilityType["施設種別 / pcd:FacilityType"] {
                <<Enumeration>>
                %% 詳細はコード定義および外部標準参照
            }
        }

        %% リレーション（UML/Mermaid標準準拠）
        AbstractFacilityManagementBase <|-- Facility
        Facility "0..*" --> "1" Address : FK pd:addressId
        Facility "1" *--> "1" MultilingualString : pd:name
        Facility "0..*" --> "1" FacilityType : pd:facilityType
      ```

2. **繰り返し実行と確認**
   - 担当者は、CSVから処理したい `分類` を順次指定し、各ドメインの図が確定するまで対話を継続すること。
