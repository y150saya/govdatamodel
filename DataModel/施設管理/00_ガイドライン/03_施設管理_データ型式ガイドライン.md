# 施設管理_データ型式ガイドライン

## 1. 目的
本ガイドラインは、行政の施設管理データモデルの相互運用性を確保するため、入力Excelとの対応、データ型、必須区分、キー、単位、コードリスト、統制語彙およびプレフィックスの定義方法を定めるものである。

---

## 2. 論理データ型定義

### 2.1 入力Excelとの対応

- `01_インプット/公共施設with防災・ファシマネ属性.xlsx` を一次情報とする。
- 元Excelはインプット原本とし、確認・整理・変換の結果は正本データ一式へ記録する。元Excelの変更を前提としない。
- 入力Excelの「項目名」「キー」「必須区分」「データ形式」「説明・定義」は、変換後も元の値を追跡できるように保持する。
- 入力Excelのデータ形式は初期値として扱い、本ガイドラインに基づく確認後に、より具体的な論理データ型へ変換できるものとする。

## 3. 必須区分およびキー

### 3.1 必須区分

- 必須区分は入力Excelの値を基本とする。
- `◎` は必須とし、属性の多重度は原則として `[1]` とする。
- `○` は任意とし、単一値属性の多重度は原則として `[0..1]` とする。
- 複数値を許容する項目は、必須区分とは別に最大数を確認し、`[0..*]` または `[1..*]` を設定する。
- 必須区分が空欄または上記以外の場合は推測で補完せず、要確認として記録する。

### 3.2 PKおよびFK

- 入力Excelの「キー」欄にある `PK` および `FK` は、データモデルCSV、クラス図および定義書に引き継ぐ。
- `PK` は各レコードを一意に識別する属性として定義し、必須とする。
- 独立したレコードとして管理するクラスにPKを定義する。値型・抽象クラスには独立したPKを一律に追加しない。複合キーの場合は構成属性と組合せの一意性を記録する。
- `FK` は参照先のクラス、参照先属性および関係の多重度を記録する。
- 属性の多重度とリレーション両端の多重度は別に管理する。FKを持たない継承・値の内包等も関係定義として記録する。
- FK属性はクラスの属性として保持し、併せてクラス間の関係線を記述する。
- 外部システムのコードやIDを参照する項目は、参照先をモデル内クラスとして定義するか、外部参照として扱うかを区別する。

## 4. 単位

- 数値（物理量）を扱う項目には、データモデル上の独立した情報として単位を設定する。
- 単位は数値に埋め込まず、データ値と分離して管理する。単位を持たない項目は単位欄を空欄とする。
- SI単位およびUCUMで表現可能な単位は、標準的な単位記号を優先する。通貨コードはISO 4217など、対象分野の標準がある場合はその表記を利用する。
- 人、件、台、棟などの計数単位は、表示用単位として明示し、物理単位と区別する。
- 単位を設定する項目には、少なくとも「単位名称」「単位記号」「準拠規格または出典」を記録する。
- 入力Excelの説明文に単位が記載されている場合は、その内容を抽出して単位欄の初期値とし、値域や計算式と整合しているか確認する。
- 単位の正本はデータモデルCSVまたは単位一覧とし、HTML定義書に表示する。クラス図では描画せず、正本から生成した `%% 単位:…` コメントを対象属性の直後に保持し、AI等がソースから読み取れるようにする。

## 5. 外部コードリストおよび統制語彙

### 5.1 基本方針

- 区分、種別、状態、行政区域、施設分類など、選択値を持つ項目はコードリストまたは統制語彙として管理する。
- 適用可能な公的・標準的なコードリストまたは統制語彙が存在する場合は、その利用を前提とする。
- 独自コードを新設する前に、国・自治体等の公的機関、国内外の標準化機関、GIFおよび関連分野の標準を確認する。
- 標準が施設管理上の要件を満たさない場合に限り、標準との対応表を保持したうえでプロジェクト固有コードを定義する。

### 5.2 確認および記録項目

出典、管理主体、バージョン、ライセンス等の記述方法は、`05_施設管理_メタデータガイドライン.md` に従う。

- コードまたは語彙の名称
- 種別（外部コードリスト、外部統制語彙、プロジェクト固有コード等）
- 提供者または管理主体
- バージョン、改定日または適用時点
- 参照URIまたは出典URL
- コード値、優先ラベル、同義語および定義
- 利用条件またはライセンス
- 入力項目との対応関係および変換規則

### 5.3 実装上の扱い

- 先頭のゼロを保持する必要があるコード値は文字列として扱う。
- 外部コードを利用する場合は、値を独自に改変せず、必要に応じてローカル表示名または対応表を追加する。
- コードリストまたは統制語彙を参照する属性には、参照先の識別子を記録する。
- 標準の確認が完了していない項目は、暫定コードを確定扱いせず、要確認として管理する。

## 6. プレフィックス定義

プロジェクト共通で名前空間プレフィックスを付与する。英字2文字または英字3文字と `:` の組み合わせを基本とする。
プレフィックスと名前空間URIの対応はプレフィックス一覧で一元管理する。

- pd: Public Data : 共通公共データ
- ac: Activity : 共通動的データ
- ad: Administrative procedures : 行政手続データ
- pcd: Property Code Data : 統制語彙
- schema: Schema.org : 外部標準語彙
- dcat: Data Catalog Vocabulary : データセット、配布形式およびカタログ
- dct: Dublin Core Metadata Terms : 共通メタデータ
- rdfs: RDF Schema : ラベル、定義および外部参照
- xsd: XML Schema : 標準データ型
- skos: Simple Knowledge Organization System : 統制語彙
- geo: OGC GeoSPARQL : 空間データ
- foaf: Friend of a Friend : 組織およびエージェント
- vcard: vCard Ontology : 連絡先
- spdx: Software Package Data Exchange : チェックサム等の配布情報
- dqv: Data Quality Vocabulary : データ品質の評価および測定結果

施設管理データモデルのクラスおよびプロパティには原則として `pd:`、コードリストおよび統制語彙には原則として `pcd:` を付与する。外部標準の要素を直接参照する場合は、その標準で定義されたプレフィックスを使用する。

工程11は実施未定である。それまではプロジェクト固有の正式URI欄を未設定とし、確認状態を別項目で管理する。仮URIを説明や検証に使う場合は例示と明記し、`example.org` 等を正式URIとして出力しない。確認済みの外部標準URIは、プロジェクト固有URIと区別して参照する。

## 7. 将来検討用のプロンプト例（現行工程の適用対象外）

以下は過去の検討例を保持するものであり、施設管理データモデル整備計画の工程1～10に適用する生成指示ではない。JSON-LD Context等は必要性を確認した場合の拡張候補とし、正式URIの整備は工程11の実施判断に従う。

再利用する場合は、JSON-LDとJSON Schemaの仕様、意味定義と検証用スキーマの参照方法、外部語彙の直接採用、独自データ型の定義、例示用名前空間および制約の保持方法を再確認して改訂する。本例よりも、本ガイドライン第1～6節と整備計画の確定方針を優先する。

```text
# 役割定義：サービス・ドメインアーキテクト
あなたは、日本の行政データ標準（GIF）とグローバル標準（セマンティックWeb / Schema.org）を最適にブリッジする「サービス・ドメインアーキテクト」です。
提供されたCSV定義（GIFコアデータモデル等）から、JSON-LD Context (`.semantic.json`) およびバリデーションスキーマ (`.schema.json`) を生成する際は、以下の「意味（Core）と制約（Profile）の分離ルール」を厳守してください。

## 1. プレフィックス（名前空間）の定義
すべての Context ファイルには、以下のプレフィックスを土台として設定すること。
- `pd:` : https://example.org/ns/pd# (Public Data / クラス・プロパティ用)
- `pcd:` : https://example.org/ns/pcd# (Property Code Data / 統制語彙・カスタム論理型用)
- `schema:` : http://schema.org/ (グローバル標準マッピング用)
- `rdfs:` : http://www.w3.org/2000/01/rdf-schema# (メタデータ用)
- `xsd:` : http://www.w3.org/2001/XMLSchema# (標準データ型用)
- `skos:` : http://www.w3.org/2004/02/skos/core# (コードリスト概念用)

## 2. Semantic層 (`@context`) の生成ルール（ロスレス・ハイブリッド構成）
この層は「純粋な意味の辞書」です。物理的な入力制約は絶対に含めないこと。

1. **クラスとプロパティの保護 (@id)**:
   - 全て `@id` は `pd:xxxxx` とし、日本の精緻な行政定義の粒度を死守すること。
   - `schema.org` に直接マッピングせず、必ず `rdfs:seeAlso` を使って「ヒント」として外部参照させること。
2. **論理データ型のマッピング (@type)**:
   - **標準型**: 純粋なテキスト、日付、数値にはW3C標準を使用する。（例: `xsd:string`, `xsd:date`, `xsd:integer`, `xsd:decimal`）
   - **GIFカスタム型**: コード値や識別子として意味を持つ文字列には、単なるstringに丸めずGIF独自の論理型を使用する。（例: `pcd:Code`, `pcd:Identifier`）
   - **統制語彙 (SKOS) 参照**: 性別などのコードリスト（pcd:xxx）を値にとるプロパティは `@type: "@id"` とする。
   - **空間データ**: OGC WKT形式のデータは `geo:wktLiteral` とする。
   - **期間**: スラッシュ区切りの期間は `xsd:string` とする。
3. **メタデータの完備**:
   - `rdfs:label` に日本語の項目名を、`rdfs:comment` に説明文を記載する。
   - ただし説明文から「最大数N」「全角・半角」「配列」などの物理的ルールは読み飛ばす（Dropする）こと。

## 3. Profile層 (`.schema.json`) の生成ルール（物理制約の適用）
この層は「システム入力時のバリデーション」です。

1. **意味の継承**:
   - 必ず `$ref` を使用して Semantic層 (`.semantic.json`) の該当プロパティを参照し、意味を引き継ぐこと。
2. **物理制約の強制**:
   - CSVに指定された「最大数（多重度）」に基づき、`type: "string"` または `type: "array"` を正しく定義すること。
   - 「半角」「全角」「桁数」などの制約は、`pattern` (正規表現) や `maxLength` で厳密に表現すること。
```
