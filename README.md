# Go Government Data Model (govedatamodel)

本リポジトリは、行政データモデル等の標準化・テンプレート管理を行うためのリポジトリです。複数メンバーで安定して保守・運用を行うための運用ガイドラインおよび開発フローを以下に定めます。

---

## 1. 運営体制と役割分担

運営メンバーは以下の役割に基づいてリポジトリの管理・運用を行います。

* **管理者 (Admin)**
  * リポジトリ設定の変更、権限管理、Branch Protection等の設定を行います。
  * リリース管理および最終的なコンフリクト解消などを担当します。
* **運営メンバー (Maintainer / Writer)**
  * Issueの起票、機能追加・修正のためのブランチ作成、Pull Request (PR) の作成および相互レビューを行います。
  * レビューが完了したPRのマージ作業を行います。

---

## 2. 開発・運用フロー

複数人での開発・更新は、**GitHub Flow** に準拠して行います。

### 2.1. ブランチ戦略
* **`main` ブランチ**
  * 本番（リリース）用ブランチです。
  * **`main` ブランチへの直接プッシュ（直マージ）は原則禁止**とします。すべての変更はPRを経由する必要があります。
  
  > [!TIP]
  > **プライベートリポジトリにおけるルール適用について**
  > メンバー全員に書き込み権限がある場合、技術的には直接プッシュやセルフマージが可能です。そのため、本ガイドラインは「チーム内の共通約束事（紳士協定）」として全員で遵守します。
  > 設定が可能であれば、GitHubの `Settings -> Branches` から **Branch Protection Rules** を有効にし、`main` ブランチへの直プッシュ禁止やレビュー必須化を強制設定することを推奨します。
* **作業ブランチ**
  * `main` から分岐し、以下の命名規則に従って作成します。
    * 新機能・データモデル追加: `feature/作業内容` (例: `feature/add-address-model`)
    * 修正・ブラッシュアップ: `fix/作業内容` (例: `fix/typo-readme`)
    * ドキュメント・ルール変更: `docs/作業内容` (例: `docs/update-rules`)

### 2.2. 新規フォルダ（ディレクトリ）作成ルール
* **権限とプロセス**
  * リポジトリのルート直下（最上位）に新しくフォルダを追加する場合は、構成が複雑化するのを防ぐため、**必ず事前にIssueを起票してメンバー間で合意**を得てから作成してください。
  * 既存フォルダ配下へのサブフォルダ作成は、事前合意なしでPRを作成して構いません。
* **技術的な手順**
  * Gitの仕様上、空のフォルダはコミットおよび追跡できません。
  * 新しいフォルダを作成する際は、必ずフォルダ内に空のプレースホルダーファイル **`.gitkeep`** を配置するか、説明用の **`README.md`** を作成してください。

### 2.3. コミット・PR・マージルール
* **コミットメッセージ**
  * コミットの要約（タイトル）の先頭に、変更内容がわかるタグを付与することを推奨します。
    * 例: `[add] 住所モデルの追加`, `[fix] 誤字の修正`, `[update] SLA記述の更新`
* **Pull Request (PR)**
  * PRのタイトルと説明には「何を変更したか」だけでなく、「なぜその変更を行うのか（背景・理由）」を簡潔に記述してください。
* **マージ基準**
  * **1名以上の運営メンバーによるレビュー（Approve）** を必須とします。自分自身で作成したPRをセルフマージすることは禁止です。
  * 自動テストやリンター（CI）が設定されている場合は、すべてのチェックがパスしていることを確認してください。
  * マージ後は、不要になった作業ブランチを速やかに削除してください。

## 3. コントリビューションガイドライン（外部向け）

外部のコラボレーターやユーザーからの提案については、当面の間以下の通り制限を設けて運用します。

* **基本方針**: 現在、原則として外部からの直接のPull Requestマージは受け付けていません。
* **例外ルール**: 軽微な修正（誤字脱字の修正、明らかな表現の調整など）に限り、Issueを起票した上でPull Requestを作成することを許可します。
* **大きな提案**: 構造変更や方針決定に関わる提案は、必ず先にIssueで相談してください。

## 4. 対応目安（SLA: Service Level Agreement）

運営メンバーは、以下の目安に従ってリポジトリ内の活動に対応します。

### 4.1. 対応時間の目安
* **Issueへの一次対応**
  * 原則として **1〜2週間以内** にコメントまたはラベル付与を行います。
* **Pull Requestのレビュー**
  * 原則として **2週間以内** にレビューまたはステータスに関するコメントを行います。

> [!NOTE]
> 上記はあくまで目安であり、時期やメンバーのリソース状況により遅れる可能性があります。本プロジェクトはボランティアベースの運用を前提としています。

### 4.2. 対応範囲の考え方
* **対応対象**
  * テンプレートの内容や構成に関する変更・改善
  * 用語の統一や表現の整理
  * OSPOスターターキットの全体方針・位置づけに関する調整
* **SLA対象外（対応不可）**
  * 個別の組織事情に踏み込んだコンサルティング
  * リポジトリ外部のシステム設定、ネットワーク、認証等のトラブルシューティング
  * その他、テンプレート内容に直接関係のない事柄
